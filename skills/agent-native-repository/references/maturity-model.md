# Maturity model

Classify only observable repository behavior. A file name alone does not prove a capability works.

## Level 0 — Conversation-carried

Typical evidence:

- important state exists mainly in chat or individual memory;
- no canonical verification command;
- completion depends on producer claims;
- new workers broadly rediscover the repository.

Recommended increment: a tiny constitution, one bounded Work Item, and one canonical verification entrypoint.

## Level 1 — Orientable

Required evidence:

- small root agent/human instructions;
- durable domain and decision location;
- task-scoped current state or equivalent issue state;
- a context command that reports dirty Git state and current work without assuming a clean clone.

Recommended increment: bind verification results to exact state.

## Level 2 — Verifiable

Required evidence:

- one canonical candidate verifier with meaningful exit codes;
- structured or referenced raw evidence;
- completion contract requiring verification;
- affected checks and public contracts are discoverable.

Recommended increment: route common mechanical work through semantic capabilities and reduce output.

## Level 3 — Tool-aware

Required evidence:

- curated capability registry or an equivalent explicit mapping;
- deterministic tool routing before model reasoning;
- raw versus model-visible output boundary;
- evidence reuse/invalidation rules;
- fast affected profile distinct from deliberate full verification.
- task cancellation, terminal outcomes, event delivery, and owned resources have deterministic lifecycle behavior.

Recommended increment: make replacement and parallel workers revision-safe.

## Level 4 — Agent-resilient

Required evidence:

- task/stage/candidate leases or equivalent duplicate-work prevention;
- isolated branches/worktrees for parallel changes;
- compact structured worker handoffs;
- source-blind public-path QA;
- combined-state integration verification;
- stale evidence rejected after relevant change.

Recommended increment: observe repetition and measure automation economics.

## Level 5 — Self-improving

Required evidence:

- schema-valid operational traces without private reasoning capture;
- human-readable evidence dashboard or reports;
- read-only repetition and router-miss analysis;
- reviewed automation promotion and retirement lifecycle;
- cost per verified accepted task tracked alongside quality and escaped defects.

Level 5 never means self-authorizing changes. Automation candidates pass the same gauntlet as production code.

## Reporting contract

Report:

- demonstrated level;
- partial capabilities above that level;
- missing or unobserved evidence;
- risks of the current state;
- smallest next increment;
- what was inspected versus executed.

Do not average levels into a score that hides a missing authority or evidence boundary.
